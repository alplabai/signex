- **Extension API (#2495)** — a binary built on `signex-app` can install its own extensions at startup through `signex_app::launch::run`; each one receives its own messages and adds commands, panels, menu rows, Start-screen sections and preferences under an `ext.<name>.` id. The Community binary installs none and is unchanged. See `docs/EXTENSION_API.md`.
- **Extension panels, rows, Start-screen sections and preferences (#2495)** — an extension adds dock panels (a stable `ext.<name>.` layout key, a title, a home dock region and its own view and update hooks), menu bar rows and PCB Active Bar rows that run its commands through the same path as every built-in row, sections in the Start screen's Home slot, and preferences kept in `prefs.json` under its own keys. A saved dock layout keeps an extension panel key whose extension is not installed and writes it back where it stood.
- **One request path (#2495)** — menu rows, keys, the palette, the agent socket and `signex-cli` run a command through one function, `Signex::run_command_request`, and read its result as one typed outcome: answered, ran, refused (with why) or failed. An agent request can carry `if_revision`: it runs only while its document is still at that revision, and is refused with nothing changed once the document moved, also when it waited for its reads and the document moved meanwhile. See `docs/EXTENSION_API.md`, "One request path".
- **Extension catalog commands (#2495)** — an extension adds commands with ids under its own `ext.<name>.` prefix; they run through the same command path as built-in ones from a key binding, a menu row or a headless run, and each says whether it runs headless or only in a window. An id that is or reads as a built-in command, lies outside the prefix or repeats is refused, and the extension is not installed. Built-in command ids are unchanged. Every id an extension adds is `ext.<name>.` and exactly one snake_case segment. A menu or Active Bar row must run a command its extension added. The agent socket refuses extension commands in this version.
- **Example extension (#2495)** — a worked example that adds a dock panel, a Tools menu row and a catalog command, labelled by its own `.ftl` file, and drives each from the application, headless and through the request path; `docs/EXTENSION_API.md` walks through it.
- **Extensions in the app's own lists (#2495)** — an installed extension's panels are listed in the status bar's panel list and under View ▸ Extensions; its commands appear in the command palette and the keyboard shortcuts with the extension's name and can be bound to keys (a binding whose extension is not installed is kept and shown as unavailable); each extension with preferences gets a Preferences page listing them with their kinds and values; and an extension can ship its own `.ftl` messages, namespaced under `ext-<name>-` and following the app language. With no extension installed every list, menu and page is unchanged.
- **A key for any command (#2495)** — Preferences ▸ Keyboard shortcuts lists every command that has no key, built-in or from an installed extension, as an Unbound row. In a custom profile, Edit opens the recorder and OK gives the command the recorded key, saved in that profile; OK after Clear takes a row's key away. The built-in profiles stay read-only (Create copies one first), and Export… writes the profile file crash-safe.
